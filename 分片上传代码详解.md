# 分片上传代码详解

> 基于 `blog_backend` 项目中的 OSS（对象存储）模块  
> 涉及文件：`CustomMinioClient.java`、`MinioUtils.java`、`MinioProperties.java`、`FileController.java`

---

## 一、整体架构概览

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  FileController │────▶│   MinioUtils    │────▶│ CustomMinioClient│
│   (HTTP入口)     │     │  (业务逻辑层)    │     │   (SDK封装层)     │
└─────────────────┘     └─────────────────┘     └─────────────────┘
                                                        │
                                                        ▼
                                                ┌───────────────┐
                                                │  MinioClient  │
                                                │ (官方SDK底层)  │
                                                └───────────────┘
                                                        │
                                                        ▼
                                                ┌───────────────┐
                                                │  S3兼容服务端  │
                                                │(MinIO/R2/OSS) │
                                                └───────────────┘
```

**设计思想**：
- **CustomMinioClient**：继承官方 `MinioClient`，封装 S3 分片上传的 5 个底层 API，提供更语义化的方法名
- **MinioUtils**：业务工具类，负责文件切片、线程池并发上传、协调分片合并
- **MinioProperties**：配置实体，映射 `application.yml` 中的 `minio.blog.*` 配置

## 二、MinioProperties — 配置实体

```java
@ConfigurationProperties(prefix="minio.blog")
public class MinioProperties implements Cloneable {
    private String endpoint;      // 对象存储服务端点

    private String video;         // 视频存储路径前缀
}
```

### 配置项详解

| 字段名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| `endpoint` | String | 对象存储服务的访问地址 | `https://xxx.r2.cloudflarestorage.com` |
| `accessKey` | String | 访问密钥 ID（类似用户名） | `your-access-key-id` |
| `secretKey` | String | 访问密钥密码（类似密码） | `your-secret-access-key` |
| `bucketsName` | String | 存储桶名称（Bucket） | `myblog-files` |
| `image` | String | 图片文件在桶内的目录前缀 | `images/` |
| `video` | String | 视频文件在桶内的目录前缀 | `videos/` |

### 对应 YAML 配置

```yaml
minio:
  blog:
    endpoint: https://xxx.r2.cloudflarestorage.com
    accessKey: your-access-key
    secretKey: your-secret-key
    bucketsName: myblog-bucket
    image: images/
    video: videos/
```

> **注意**：`image` 和 `video` 不是文件类型校验，而是**对象存储中的目录前缀**。最终文件路径为：`{video}{fileName}`，如 `videos/2024-06-15demo.mp4`。

### 3.2 initMultiPartUpload — 初始化分片上传

```java
public String initMultiPartUpload(
    String bucket,                    // 存储桶名称
    String region,                    // 区域（通常传 null）
    String object,                    // 对象/文件名
```

#### 参数详解

| 参数 | 类型 | 必填 | 说明 |

| `bucket` | String | 是 | 存储桶名称，如 `myblog-bucket` |
| `region` | String | 否 | 服务端区域，R2/MinIO 通常传 `null` |

| 类型 | 说明 |

### 3.3 uploadMultiPart — 上传单个分片

```java
public UploadPartResponse uploadMultiPart(
    String bucket,                    // 存储桶名称
    String region,                    // 区域（通常传 null）
    String object,                    // 对象/文件名
    Object data,                      // 分片数据（byte[]）
    long length,                      // 数据长度（字节数）
    String uploadId,                  // 初始化时获取的 uploadId
    int partNumber,                   // 分片序号（从 1 开始）
    Multimap<String, String> headers, // HTTP 请求头
    Multimap<String, String> extraQueryParams  // 额外查询参数
)
```

#### 参数详解

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `bucket` | String | 是 | 存储桶名称 |
| `region` | String | 否 | 区域，通常传 `null` |
| `object` | String | 是 | 对象路径 |
| `data` | `Object` | 是 | 分片数据，实际传入 `byte[]` |
| `length` | `long` | 是 | 本次分片的实际字节数 |
| `uploadId` | String | 是 | 分片上传会话 ID |
| `partNumber` | `int` | 是 | 分片序号（**必须从 1 开始递增**） |
| `headers` | `Multimap<String, String>` | 否 | 请求头，如 `Content-Type` |
| `extraQueryParams` | `Multimap<String, String>` | 否 | 扩展查询参数，通常传 `null` |

#### 返回值

| 类型 | 说明 |
|------|------|
| `UploadPartResponse` | 包含 `etag`（分片校验标识），合并时必须提供 |

#### 重要约束
- `partNumber` 必须**连续递增**，最小为 1
- 除最后一片外，每片大小**不得低于 5MB**（S3 标准限制）
- 同一个 `uploadId` 下，每个 `partNumber` 只能上传一次，重复上传会覆盖

### 3.4 mergeMultipartUpload — 合并分片

```java
public ObjectWriteResponse mergeMultipartUpload(
    String bucketName,                // 存储桶名称
    String region,                    // 区域（通常传 null）
    String objectName,                // 对象/文件名
    String uploadId,                  // 分片上传会话 ID
    Part[] parts,                     // 所有分片的元信息数组
    Multimap<String, String> extraHeaders,      // 额外请求头
    Multimap<String, String> extraQueryParams   // 额外查询参数
)
```

#### 参数详解

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `bucketName` | String | 是 | 存储桶名称 |
| `region` | String | 否 | 区域，通常传 `null` |
| `objectName` | String | 是 | 对象路径 |
| `uploadId` | String | 是 | 分片上传会话 ID |
| `parts` | `Part[]` | 是 | 分片元信息数组，每个元素包含 `partNumber` 和 `etag` |
| `extraHeaders` | `Multimap<String, String>` | 否 | 额外请求头，通常传 `null` |
| `extraQueryParams` | `Multimap<String, String>` | 否 | 额外查询参数，通常传 `null` |

#### `Part` 结构

```java
new Part(partNumber, etag)
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `partNumber` | `int` | 分片序号，必须与上传时一致 |
| `etag` | `String` | 分片上传成功后返回的校验标识 |

#### 返回值

| 类型 | 说明 |
|------|------|
| `ObjectWriteResponse` | 包含最终对象的 `etag`、`versionId` 等信息 |

#### 底层原理
对应 S3 API `CompleteMultipartUpload`。服务端收到请求后，按 `parts` 数组的顺序将各分片拼接成完整文件，然后删除临时分片。

> ⚠️ **关键**：`parts` 数组必须**按 `partNumber` 顺序排列**，否则合并后的文件会损坏！

## 四、MinioUtils — 业务逻辑层

```java
@Component
public class MinioUtils {
    private final CustomMinioClient customMinioClient;  // SDK 封装客户端
    private final MinioProperties minioProperties;      // 配置属性
    private final ThreadPoolTaskExecutor threadPool;    // 线程池（用于并发上传分片）
    static final long CHUNK_SIZE = 0x500000L;           // 分片大小：5MB（十六进制写法，等同于 5242880）
    private static CountDownLatch countDownLatch;       // 线程同步计数器
}
```

### 常量与字段详解

| 名称 | 类型 | 值 | 说明 |
|------|------|-----|------|
| `CHUNK_SIZE` | `long` | `0x500000L` | 每个分片大小为 **5MB**（十六进制 `0x500000` = 十进制 `5242880` 字节） |
| `countDownLatch` | `CountDownLatch` | `static` | 用于等待所有分片上传完成后再执行合并 |

> **为什么选 5MB？** 这是 S3 协议规定的最小分片大小（最后一片除外）。如果分片小于 5MB，服务端会拒绝上传。

### 4.1 uploadImage — 普通上传（小文件）

```java
public void uploadImage(String fileName, MultipartFile file)
```

#### 参数详解

| 参数 | 类型 | 说明 |

- **适用场景**：小文件（如图片，通常几 MB 以内）
- **简单直接**：不需要管理 uploadId、分片序号、合并等复杂逻辑

### 4.2 uploadPartFile — 分片上传（大文件）

```java
public void uploadPartFile(String fileName, MultipartFile file)
```

#### 参数详解

| 参数 | 类型 | 说明 |
|------|------|------|
| `fileName` | String | 最终存储的文件名，由控制器生成（带日期前缀） |
| `file` | `MultipartFile` | Spring 封装的 HTTP 上传文件对象 |

#### 完整执行流程

```
Step 1: 初始化分片上传
    └── getUploadId(finalName, contentType) 
        └── customMinioClient.initMultiPartUpload(...)
            └── 返回 uploadId

Step 2: 计算分片数量
    └── chunkCount = (totalLength + CHUNK_SIZE - 1) / CHUNK_SIZE
    └── 向上取整，如 12MB 文件 → 3 个分片

Step 3: 并发上传分片（多线程）
    └── 创建 CountDownLatch(chunkCount)
    └── for i in 0..chunkCount-1:
        └── threadPool.submit(() -> processChunk(i+1, ...))
    └── countDownLatch.await()  // 阻塞等待所有分片上传完成

Step 4: 合并分片
    └── MergeFile(finalName, uploadId, chunkCount)
        └── listMultipart()  // 查询所有分片
        └── mergeMultipartUpload()  // 合并
```

#### 分片计算逻辑

```java
long totalLength = file.getSize();                          // 文件总大小
long chunkCount = (totalLength + CHUNK_SIZE - 1) / CHUNK_SIZE;  // 向上取整

// 示例：12MB 文件
// chunkCount = (12582912 + 5242880 - 1) / 5242880 = 3
```

#### 多线程并发上传

```java
countDownLatch = new CountDownLatch((int)chunkCount);  // 初始化计数器

for (int i = 0; i < chunkCount; i++) {
    long position = (long)i * CHUNK_SIZE;              // 当前分片在文件中的起始位置
    int readSize = (int)Math.min(CHUNK_SIZE, totalLength - position); // 当前分片实际大小
    int partNumber = i + 1;                             // 分片序号（从 1 开始）
    
    this.threadPool.submit(() -> {
        this.processChunk(partNumber, finalName, file, position, readSize, uploadId);
        countDownLatch.countDown();  // 当前分片上传完成，计数器减 1
    });
}

countDownLatch.await();  // 主线程阻塞，直到所有分片上传完成
```

**为什么用线程池？**
- 网络 I/O 是阻塞操作，单线程串行上传会浪费大量等待时间
- 多线程可以**并发发送多个分片**，显著提高上传速度（前提是带宽和网络条件允许）
- `CountDownLatch` 确保**所有分片都上传成功后**，才执行合并操作

### 4.4 processChunk — 处理单个分片上传

```java
private void processChunk(
    int chunkIndex,        // 分片序号（从 1 开始）
    String finalName,      // 对象路径
    MultipartFile file,    // 原始文件
    long position,         // 分片在文件中的起始偏移量（字节）
    int readSize,          // 当前分片需要读取的字节数
    String uploadId        // 分片上传会话 ID
)
```

#### 参数详解

| 参数 | 类型 | 说明 |
|------|------|------|
| `chunkIndex` | `int` | 分片序号，从 1 开始递增，对应 S3 的 `partNumber` |
| `finalName` | String | 对象在存储桶中的完整路径 |
| `file` | `MultipartFile` | 原始上传文件，用于获取输入流 |
| `position` | `long` | 当前分片在文件中的起始位置（字节偏移量） |
| `readSize` | `int` | 当前分片的大小（字节数） |
| `uploadId` | String | 分片上传会话 ID |

#### 执行逻辑

```java
// 1. 创建缓冲区
byte[] buffer = new byte[readSize];

// 2. 获取文件输入流并定位到分片起始位置
InputStream inputStream = file.getInputStream();
inputStream.skip(position);  // 跳过前面已读的字节

// 3. 读取当前分片的数据
int bytesRead = inputStream.read(buffer);  // 实际读取的字节数

// 4. 构造请求头
HashMultimap headers = HashMultimap.create();
headers.put("Content-Type", "application/octet-stream");

// 5. 上传分片
UploadPartResponse response = this.customMinioClient.uploadMultiPart(
    this.minioProperties.getBucketsName(),  // 存储桶
    null,                                    // region
    finalName,                               // 对象路径
    buffer,                                  // 分片数据（byte[]）
    (long)bytesRead,                         // 实际读取的字节数
    uploadId,                                // 会话 ID
    chunkIndex,                              // 分片序号
    headers,                                 // 请求头
    null                                     // extraQueryParams
);

// 6. 打印日志并释放计数器
System.out.println("chunk[" + chunkIndex + "] buffer size: [" + buffer.length + " Byte] upload etag: [" + response.etag() + "]");
countDownLatch.countDown();  // 通知主线程：当前分片已完成
```

#### 关键点
- **流的定位**：每个线程独立打开 `InputStream`，通过 `skip(position)` 跳到各自负责的分片位置，**避免多线程争抢同一个流指针**
- **实际读取字节数**：`bytesRead` 可能小于 `readSize`（流末尾），所以传给 SDK 的是 `bytesRead` 而不是 `buffer.length`
- **Content-Type 固定为 `application/octet-stream`**：分片只是二进制数据块，不需要具体的 MIME 类型，合并后的文件类型由初始化时的 `Content-Type` 决定

### 4.5 MergeFile — 合并所有分片

```java
private void MergeFile(String finalName, String uploadId, long chunkCount)
```

#### 参数详解

| 参数 | 类型 | 说明 |
|------|------|------|
| `finalName` | String | 对象路径 |
| `uploadId` | String | 分片上传会话 ID |
| `chunkCount` | `long` | 总分片数量 |

#### 执行逻辑

```java
// 1. 创建 Part 数组
Part[] parts = new Part[(int)chunkCount];

// 2. 从服务端查询所有已上传的分片信息
ListPartsResponse partResult = this.customMinioClient.listMultipart(
    this.minioProperties.getBucketsName(),  // 存储桶
    null,                                    // region
    finalName,                               // 对象路径
    10000,                                   // maxParts：最多查 10000 个
    0,                                       // partNumberMarker：从第 1 个开始
    uploadId,                                // 会话 ID
    null,                                    // extraHeaders
    null                                     // extraQueryParams
);

// 3. 构造 parts 数组（必须按 partNumber 顺序）
int partNumber = 1;
for (Part part : partResult.result().partList()) {
    parts[partNumber - 1] = new Part(partNumber, part.etag());
    partNumber++;
}

// 4. 调用合并
this.customMinioClient.mergeMultipartUpload(
    this.minioProperties.getBucketsName(),  // 存储桶
    null,                                    // region
    finalName,                               // 对象路径
    uploadId,                                // 会话 ID
    parts,                                   // 分片元信息数组
    null,                                    // extraHeaders
    null                                     // extraQueryParams
);
```

#### 为什么需要 `listMultipart`？

虽然客户端本地知道应该有多少个分片，但**多线程并发上传时，可能存在上传失败或重试的情况**。通过 `listMultipart` 从服务端查询：
1. **确认所有分片都已上传成功**
2. **获取每个分片的 `etag`**（服务端返回的校验值，客户端不知道）
3. **保证 `parts` 数组的顺序正确**

> ⚠️ **注意**：`listMultipart` 返回的分片列表**默认按 `partNumber` 升序排列**，但代码中还是显式按 `partNumber` 顺序构造数组，这是一种防御性编程。

### 5.1 upload — 图片上传接口

```java
@PostMapping("/upload")
public Result upload(MultipartFile file)
```

#### 参数详解

| 参数 | 类型 | 说明 |
|------|------|------|
| `file` | `MultipartFile` | HTTP multipart/form-data 中的文件字段 |

#### 执行流程

```java
// 1. 生成带时间戳的文件名
String finalName = LocalDateTime.now() + file.getOriginalFilename();
// 示例："2024-06-15T10:30:00demo.jpg"

// 2. 异步上传（新建线程，不阻塞 HTTP 响应）
new Thread(() -> {
    try {
        this.minioUtils.uploadImage(finalName, file);
    } catch (Exception e) {
        throw new BaseException("图片上传出错了");
    }
}).start();

// 3. 立即返回（上传在后台进行）
System.out.println("正在上传图片，请稍等");
return Result.success(this.articleService.addArticle(finalName));
```

#### 设计特点
- **异步上传**：新建线程执行上传，HTTP 请求立即返回，用户体验更好
- **先写数据库，后上传文件**：`articleService.addArticle(finalName)` 先记录文件元数据到数据库，然后后台慢慢上传。如果上传失败，数据库里会有一条" orphaned "记录
- **线程安全问题**：每个请求 new 一个 Thread，没有复用线程池，高并发时可能耗尽系统资源（建议使用 `threadPool` 而不是 `new Thread()`）

- **返回文件名**：前端拿到 `finalName` 后，可以拼接成完整的对象存储访问 URL

## 七、关键设计要点总结

### 1. 为什么需要分片上传？

| 场景 | 普通上传 (`putObject`) | 分片上传 (`multipart`) |
|------|------------------------|------------------------|
| 文件大小 | 适合小文件（< 100MB） | 适合大文件（> 100MB） |
| 网络中断 | 需要重新上传整个文件 | 只需重传失败的分片 |
| 并发能力 | 单线程 | 多线程并发上传 |
| 内存占用 | 一次加载整个文件 | 每次只加载一个分片（5MB） |
| 服务端限制 | 单次请求有大小上限 | 理论上无上限（分片数最多 10000） |

### 2. 线程安全如何保证？

- **每个分片独立打开 InputStream**：`processChunk` 中每个线程都调用 `file.getInputStream()` 创建新的流，再通过 `skip(position)` 定位，**不存在多个线程共享同一个流的问题**
- **CountDownLatch 同步**：主线程通过 `await()` 阻塞，直到所有分片上传线程调用 `countDown()`，确保**合并操作在所有分片完成后执行**
- **S3 服务端保证**：同一个 `uploadId` + `partNumber` 重复上传会覆盖，但最终合并时以最后一次上传为准

### 3. 异常处理有什么不足？

当前代码的异常处理比较粗糙：

```java
try {
    this.minioUtils.uploadPartFile(finalName, file);
} catch (Exception e) {
    throw new BaseException("视频上传失败了");
}
```

**问题**：
- 如果某一分片上传失败，**没有自动重试机制**
- 没有调用 `cancelMultipartUpload()` 清理服务端残留分片
- 异常信息被吞掉，不利于排查问题

**改进建议**：
```java
// 在 processChunk 中加入重试逻辑
try {
    this.customMinioClient.uploadMultiPart(...);
} catch (Exception e) {
    // 重试 3 次
    // 仍然失败则调用 cancelMultipartUpload 清理
}
```

### 4. 为什么能无缝切换 MinIO / R2 / OSS？

因为底层都是 **S3 API 标准**：
- `initMultiPartUpload` → S3 `CreateMultipartUpload`
- `uploadMultiPart` → S3 `UploadPart`
- `mergeMultipartUpload` → S3 `CompleteMultipartUpload`
- `cancelMultipartUpload` → S3 `AbortMultipartUpload`
- `listMultipart` → S3 `ListParts`

只要修改 `MinioProperties` 中的 `endpoint`、`accessKey`、`secretKey`，代码逻辑完全不变。

## 九、常见问题 FAQ

**Q1: 分片大小必须是 5MB 吗？**  
A: 除最后一片外，每片**不得小于 5MB**。最后一片可以小于 5MB。如果文件本身小于 5MB，建议直接使用普通上传（`uploadImage`），避免分片上传的开销。

**Q2: 最多能分多少片？**  
A: S3 标准规定最多 **10000 个分片**。按每片 5MB 计算，最大支持约 **48GB** 的文件。如果需要更大，可以增大分片大小（如 100MB/片）。

**Q3: 分片上传失败怎么办？**  
A: 当前代码没有自动重试。生产环境建议：
1. 在 `processChunk` 中加入重试逻辑（最多 3 次）
2. 如果仍然失败，调用 `cancelMultipartUpload` 清理残留分片
3. 返回错误给前端，让用户重新上传

**Q4: 为什么图片用异步上传，视频用同步上传？**  
A: 图片小，上传快，异步可以提升接口响应速度。视频大，分片上传本身耗时较长，同步更便于前端展示上传进度（虽然当前代码没有实现进度反馈）。

**Q5: `CountDownLatch` 用 `static` 有什么问题？**  
A: 当前代码中 `countDownLatch` 是 `static` 的，这意味着**多个并发请求共享同一个计数器**，会导致严重的线程安全问题。建议改为**实例字段**或**方法局部变量**。
